Most reading trackers treat your to-be-read list as a dumping ground — books go in and rarely come back out unless you scroll to find them. Ledger was built to fix that: a book-tracking app that actively helps you decide what to read next, instead of just logging what you've read.

Adding books is meant to be near-instant — a barcode scan looks the title up via the Open Library API instead of a manual search. From there, full CRUD workflows carry a book across every reading state, and a custom reorder algorithm keeps the TBR queue from turning into a static list nobody looks at again.

The part of Ledger I'd point to first in an interview is the data model, not a feature. Every table is scoped per user, and access is enforced through Postgres row-level security policies — not just hidden behind frontend routes. That distinction matters: it's the difference between "the UI doesn't show you someone else's data" and "the database physically won't return someone else's data" even if the frontend check were bypassed entirely.

Custom cover uploads round it out — letting a user override the default cover art for a specific edition via Supabase Storage, tied to the same per-user, authenticated access model as everything else in the app.
